# Agent Team 组建方案与协作协议

> 本文件定义「在线考试系统」毕业设计项目的 **Agent Team**：角色、职责边界、输入输出物、交接协议、协作时序与质量门禁。
> 说明：本项目为 **1 名人类负责人 + 7 个 AI Agent 角色** 的模拟团队。人类负责选题、验收与最终拍板；7 个 Agent 由编排器（Orchestrator）按阶段调度，彼此通过**文件产物**交接（而非对话记忆），因此每一份产物都必须自包含、可被下游直接消费。

## 2. 角色 Charter（职责边界）

### RA 需求分析师
- **必须做**：识别 3 类角色 × 全生命周期的用例；把每条需求写成「编号 + 描述 + 优先级 + 验收标准」；建立 `需求 → 设计 → 接口 → 测试用例` 的追踪矩阵；区分功能/非功能需求（性能、安全、可用性、兼容性），非功能需求给出可度量指标。
- **不得做**：指定具体技术栈实现细节（那是 SA 的职责）；写代码。
- **交付判据**：≥20 条需求、≥25 个用例、追踪矩阵无孤立需求。

### SA 系统架构师
- **必须做**：给出选型对比与理由（至少 2 个备选方案）；分层架构图 + 部署图；ER 图（8 张表，含外键与索引）；≥4 张关键场景时序图（登录、开考、自动保存、交卷判分、阅卷）；API 契约与基线规格逐条对齐；说明安全设计与并发/事务策略。
- **不得做**：偏离基线规格擅自增删接口（如需变更走变更单）。
- **交付判据**：接口清单与基线 100% 一致；每张图可被 mermaid 渲染。

### FE 前端开发者
- **必须做**：按 API 契约实现全部页面；角色路由守卫；axios 拦截器统一注入 token 与错误提示；答题页倒计时（服务端 deadline 为准）、选项自动保存（防抖 + 状态提示）、交卷二次确认；表格分页、表单校验；`npm run build` 通过。
- **不得做**：前端伪造数据；把答案（answer/analysis）在交卷前渲染出来。
- **交付判据**：`npm run build` 成功；页面清单覆盖率 100%。

### BE 后端开发者
- **必须做**：严格实现 5.x 全部接口与错误码；JWT + RBAC 中间件；Repository 双实现（mysql / memory）；判分规则（多选少选/错选均不得分，判断/单选精确匹配）；超时自动交卷；统计口径与基线一致；`npm test` 全绿且覆盖率 ≥70%。
- **不得做**：SQL 字符串拼接；在响应中泄露 password_hash；跳过 service 层校验。
- **交付判据**：测试全绿 + 覆盖率达标 + 接口自测脚本通过。

### QA 测试工程师
- **必须做**：测试计划（范围/策略/环境/进度/风险）；用例表（编号、前置、步骤、预期、优先级）；分层测试（单元/接口集成/前端构建与静态检查）；执行并记录真实输出；缺陷单（编号、严重级、复现步骤、状态、回归结论）；覆盖率数据。
- **不得做**：修改业务代码来「让测试通过」（发现缺陷只登记，由开发者修复；仅可补测试代码）。
- **交付判据**：用例 ≥60 条、执行率 100%、缺陷闭环率 100%（含「已知问题」说明）。

### TW 论文撰写者
- **必须做**：6 章结构（绪论 / 相关技术与理论 / 需求分析 / 系统设计 / 系统实现与测试 / 总结与展望）；中英文摘要 + 关键词；图表编号连续；引用真实代码与真实测试数据；参考文献 ≥20 条（GB/T 7714 格式）；正文 ≥15000 字；语言为学术书面语，不用「我们」。
- **不得做**：编造未实现的功能；与代码/测试报告矛盾。
- **交付判据**：字数、图表、参考文献达标；与实现一致。

### DA 答辩助手
- **必须做**：14~16 页 PPT（封面/背景/需求/架构/数据库/关键实现/演示/测试/创新点/不足/展望/致谢）；每页要点 ≤6 条、配讲稿备注；演示脚本按分钟编排（含备用方案：现场断网/数据库异常）；预测 Q&A ≥20 条，覆盖选题、技术选型、难点、测试、创新、不足。
- **不得做**：PPT 大段文字堆砌；承诺未实现的功能。
- **交付判据**：`slides.json` 可被脚本生成 pptx；脚本总时长 8~10 分钟。

## 3. 交接协议（Handoff Contract）

1. **文件即接口**：下游只读上游文件，不依赖对话上下文。所有产物写入 `exam-system/` 下约定路径。
2. **不覆盖他人物件**：每个角色只写自己目录；跨目录修改须在 `00-team/协作日志.md` 登记。
3. **基线优先**：与 `project-brief.md` 冲突时以基线为准，并在协作日志提「变更单」。
4. **可验证**：代码类产物必须附可执行命令与真实执行结果（不得写「应该可以」）。
5. **中文交付**：文档用简体中文，代码标识符用英文，注释用中文。

## 4. 协作时序（Orchestration Timeline）

```
P0 立项       人类 ── 基线规格 ──▶ 全队
P1 需求+设计   ┌─ RA ─▶ 需求规格/用例/追踪矩阵 ─┐
               └─ SA ─▶ 架构/ER/时序/API 契约 ─┴─▶ 评审门禁 G1/G2
P2 并行开发    ┌─ BE ─▶ server + 测试 ──┐
               └─ FE ─▶ web + 构建 ─────┴─▶ 联调（契约对齐）门禁 G3/G4
P3 测试        QA ─▶ 计划/用例/执行/缺陷/报告 ──▶ 门禁 G5
P4 论文+答辩   ┌─ TW ─▶ 6 章论文 ─┐
               └─ DA ─▶ PPT/脚本/Q&A ─┴─▶ 门禁 G6/G7
P5 交付        人类验收 ─▶ 归档
```

**并行策略**：P1 的 RA 与 SA 可并行（SA 以基线为输入，需求文档为交叉校验）；P2 的 FE 与 BE 必须并行但共用同一份 API 契约，二者以「契约」而非「代码」解耦；P4 的 TW 与 DA 并行，DA 以论文终稿为准做二次对齐。

## 5. 质量门禁（Definition of Done）

见 `project-brief.md` 第 7 节 G1~G7。任一角色未过门禁，编排器打回该角色重做，不得进入下一阶段。

## 6. 沟通规则（模拟）

- **站会**：每阶段结束输出 3 行摘要（完成 / 阻塞 / 下一步），汇总进 `00-team/协作日志.md`。
- **争议仲裁**：需求 vs 实现冲突 → 基线；性能 vs 进度冲突 → 保功能完整、性能给指标不给实现；论文 vs 代码冲突 → 以代码为准改论文。
- **升级机制**：同一问题 2 轮未闭环 → 升级至人类负责人。

## 7. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 接口契约漂移 | 前后端联调失败 | 契约先行 + 集成测试按契约断言 |
| 判分规则歧义（多选） | 成绩争议 | 基线明确「少选/错选均不得分」，测试用例锁定 |
| 超时与自动交卷竞态 | 成绩丢失 | 服务端 deadline 为准，重复提交幂等 |
| 测试环境无 MySQL | 测试不可执行 | Repository 内存实现，CI 无需 DB |
| 论文与实现脱节 | 答辩被质疑 | 论文数字全部取自测试报告与代码 |
