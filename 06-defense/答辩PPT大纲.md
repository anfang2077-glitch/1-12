## 1 逐页大纲

### P1 封面（0:20）

- **版式**：封面（深蓝底 + 左侧竖蓝条）
- **标题**：基于 React + Node.js 的在线考试系统设计与实现
- **副标题**：毕业设计答辩
- **信息栏**：专业：软件工程 / 学生：XXX / 指导教师：XXX / 2026 年 6 月
- **要点**（5 项，作为封面信息而不列表）：题目、副标题、专业、学生与指导教师、答辩时间
- **配图建议**：无（保持留白，右下角可放校徽）
- **讲稿要点**：问好 → 自报专业与题目 → 一句话说明汇报结构（为什么做、怎么做、做得怎样、还缺什么）→ 提示约 10 分钟并接现场演示。
- **一句结论**：本课题交付一套可运行的七步闭环考试系统与全链路工程文档。

### P2 选题背景与意义（0:45）

- **版式**：要点（5 条）
- **要点**：
  1. 纸质考试：制卷周期以周计，阅卷统计靠人工转录
  2. 同类平台：功能冗余、答案易丢、计时不可信
  3. 课程规模：一门课一个班，宜轻量自建
  4. 目标：七步闭环，计时与判分可审计
  5. 价值：完整走通契约、实现、测试链路
- **配图建议**：自绘「纸质流转 vs 系统闭环」两列对比图（左列 7 个物理环节、右列 7 个系统步骤）。
- **讲稿要点**：先讲痛点（P-01 周期、P-04 转录、Q-03 丢答案、Q-04 计时），再讲为什么「轻量自建」适合单课程场景，最后落到「可审计」这一核心诉求。
- **一句结论**：把计时、判分、统计从人工环节变成可审计的确定性流程，是本题的真正价值。

### P3 国内外现状与问题（0:45）

- **版式**：要点（5 条）
- **要点**：
  1. 国外：机考与自适应测验成熟，重并发考务
  2. 国内：智慧教学平台普及，严肃考试管控弱
  3. 开源：Moodle 类可自建，但体量大、改造难
  4. 缺口：闭环、轻量、口径透明三者难兼得
  5. 切入：单课程尺度，机制可验证、边界诚实
- **配图建议**：调研摘要 §3 的「5 系统 × 10 维度」对比表（压缩为 5 行 × 5 列，✓/△/✘ 三态）。
- **讲稿要点**：按「国外—国内—开源」三层讲，强调不是「没人做」，而是「没有同时满足闭环、轻量、口径透明」；因此本项目主动收窄范围，并把能力边界写进文档。
- **一句结论**：不做平台，只做一门课能自建自运维的严肃考试系统。

### P4 需求分析（角色 + 用例）（0:50）

- **版式**：表格（3 列 × 5 行）
- **要点**（表格内容，4 行）：角色 / 主要用例 / 权限边界（管理员 20 个、教师 23 个、学生 12 个、合计 UC-01~UC-38 共 38 个）
- **配图建议**：`05-thesis/figures/fig-3-1-usecase.png`（用例图，38 个用例分 8 个功能域）或 `fig-3-2-module.png`（功能模块图）。
- **讲稿要点**：讲「三类角色、一条权限矩阵、38 个用例」；强调权限是「纵向角色 × 横向数据归属」双重校验，越权返回 401/403 而不是空数据；需求全部进追踪矩阵，56 条无孤立项。
- **一句结论**：需求阶段就锁定了角色边界与可验收口径，为后续设计与测试提供唯一起点。

### P5 非功能需求与指标（0:35）

- **版式**：表格（3 列 × 6 行：质量维度 / 指标要求 / 当前结论）
- **要点**：
  - 性能：P95 < 500ms、P99 < 1000ms → **未压测（缺 k6 数据）**，不写入验收结论
  - 安全：越权 100% 拦截、交卷前不泄露答案 → 集成用例通过
  - 可靠：自动保存 ≤3s、恢复偏差 ≤5s → 落库与恢复已验证，时延未实测
  - 体积：gzip 主 JS < 500KB → 实测 100.40 KB 达标
  - 可维护：用例 ≥40、行覆盖 ≥70% → 217 条、93.6% 达标
- **配图建议**：无（表格已足够）；可在页脚加一条「未测项 3 类：压测、浏览器矩阵、真机 MySQL 联调」。
- **讲稿要点**：主动交代「指标写了但没测」的部分，比被评委问出来更好；强调每条 NFR 都给了度量方法与测量工具。
- **一句结论**：非功能需求全部可度量，未测项已如实登记为残留风险。

### P6 系统架构（1:00）

- **版式**：要点（5 条）
- **要点**：
  1. 五层：表现、接口、业务、仓储、基础设施
  2. 依赖单向：路由到控制器到服务到仓储
  3. 仓储双实现：mysql 与 memory 同接口
  4. createApp 工厂注入仓储与时钟
  5. 单机部署：Nginx、Node、MySQL 三层
- **配图建议**：`fig-4-1-architecture.png`（分层架构图，主图）；`fig-4-2-deploy.png`（部署图，可缩小放右下角）。
- **讲稿要点**：讲清「为什么这样分层」——服务层不出现 req/res，仓储层不含业务分支；再讲双实现与工厂注入带来的可测试性（测试不连库、不占端口、可用假时钟验证超时）。
- **一句结论**：分层不是画图，而是靠依赖方向约束与可注入依赖落地的。

### P7 数据库设计（ER + 8 表）（0:50）

- **版式**：要点（5 条）
- **要点**：
  1. 8 张表、14 条关系，覆盖七步闭环
  2. 一人一卷：答卷表唯一键兜底并发
  3. 同卷同题唯一：试卷题目表唯一键约束
  4. 17 个二级索引，全部对应真实查询
  5. 选项与答案用 JSON，形状由服务层校验
- **配图建议**：`fig-4-3-er.png`（ER 图，主图）；角落放「8 表清单」小表（users/courses/questions/exams/exam_questions/exam_students/attempts/answers）。
- **讲稿要点**：以「考试 → 试卷题目 → 答卷 → 答题明细」四级引用链为主干讲；突出两个唯一键如何把业务规则下沉为数据库约束；主动说 JSON 字段的代价（数据库无法校验形状，校验落在服务层与导入接口）。
- **一句结论**：正确性优先——能用约束保证的规则，不靠应用层自觉。

### P8 关键流程（开考-自动保存-交卷判分）（1:10）

- **版式**：要点（5 条）
- **要点**：
  1. 开考：服务端算截止时间，重复开考回原卷
  2. 自动保存：防抖后单题提交，upsert 幂等
  3. 恢复：答案与剩余秒数均由服务端下发
  4. 交卷：事务内判分，条件更新防双写
  5. 多选：少选、错选、多选一律 0 分
- **配图建议**：`fig-4-5-sequence-exam.png`（答题全流程时序图）；可用 3 个色块标注「开考 / 保存 / 交卷」三个决策点。
- **讲稿要点**：这条链是系统最需要保证的部分，按「时间权威在服务端、写入幂等、判分唯一实现」三条主线讲；把多选规则作为「口径显式化」的例子说透（写进需求 FR-29 并用用例锁定）。
- **一句结论**：答题链路的三个不变量——不丢答案、不重复计时、不重复计分。

### P9 技术难点与解决方案（1:00）

- **版式**：要点（5 条，采用「难点 → 方案」句式）
- **要点**：
  1. 交卷竞态 → 行锁加条件更新，只写一次
  2. 计时可信 → 以 deadline 为唯一权威
  3. 保存风暴 → 防抖合并加唯一键 upsert
  4. 无库测试 → 仓储双实现加时钟注入
  5. 答案泄露 → DTO 白名单按阶段裁剪
- **配图建议**：4 象限「难点—方案」矩阵（左上竞态、右上计时、左下测试、右下安全），每格 1 个关键词 + 1 行方案。
- **讲稿要点**：每一条都先讲「如果不这样做会出什么事」，再讲方案；强调这是「机制」而非「补丁」——例如条件更新即使漏了行锁也能拦住第二次写入。
- **一句结论**：难点不在写功能，而在把并发、时间、权限三类不确定性收敛成确定性。
