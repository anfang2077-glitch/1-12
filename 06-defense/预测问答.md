## 一、选题与意义（4 题）

### Q1 为什么选「在线考试系统」这个题目？创新性在哪里？

**结论**：题目不新，我没把它当创新点卖；价值在「轻量自建 + 机制可验证」。

**回答**：选它是因为三个可验证的缺口：纸质考试的成绩要人工二次转录，错误难自查；同类平台普遍存在答案暂存本地、计时由客户端推算的问题；判分口径不透明，多选少选给不给分没有写清楚。我的做法是把这三件事做成机制：截止时间由服务端计算并下发，每次作答按单题落库，判分口径写进需求 FR-29 并用用例锁定。所以创新性体现在取舍与验证方式，不在功能清单。

**追问风险**：「这算创新吗？」→ 承认是工程型课题，创新在机制设计与验证闭环，不主张理论创新。

### Q2 和超星学习通、雨课堂、Moodle 相比，你的系统价值在哪？

**结论**：价值不在功能更多，而在闭环完整、数据自主、口径透明。

**回答**：超星、雨课堂是 SaaS，数据在第三方，二次开发受限；Moodle 能自建，但体量大、插件复杂，毕业设计周期内很难吃透。我的系统 8 张表、36 个接口，单机一条命令启动，从管理员建号到教师看统计能在一条演示路径里走完，题库与成绩全部落在本校 MySQL。对一门课一个班的场景，这种轻量自建比平台化更划算，也更容易讲清楚每一处设计理由。

**追问风险**：「功能不如人家多。」→ 对，本期主动收窄范围，把边界写进文档，而不是堆功能。

### Q3 在线考试系统很常见，工作量如何体现？

**结论**：工作量在机制与验证，不在页面数量。

**回答**：后端 36 个接口、8 张表、17 个二级索引；前端 15 个页面、15 条路由；设计阶段出了 6 张关键场景时序图和 7 组选型加权对比；测试阶段 217 条自动化用例，其中 63 条接口集成覆盖 36 个接口的正常流与异常流，35 条业务规则覆盖判分、超时、幂等、阅卷、统计；需求 56 条全部进追踪矩阵。这些都能用命令复跑，不是文档里写的「应该可以」。

**追问风险**：「代码量多少？」→ 不报未统计的行数，改报接口数、用例数与覆盖率三个可核对指标。

### Q4 这个系统能用在什么场景？谁会用？

**结论**：面向一门课、一个教学班的院系自建场景，不是万人平台。

**回答**：容量按 1 名管理员、2 名教师、50 名学生、20 场考试估算，约 1000 份答卷、2 万行答题明细，总存储不到 50MB，单台 2C4G 足够；峰值 100 人同时答题，约 33 QPS 的保存请求。适合需要数据自主、又不想维护重型平台的课程组。反过来，需要摄像头监考、多租户计费、移动端答题的场景不在范围内，我不会硬套。

**追问风险**：「50 人是不是太小？」→ 是刻意的范围选择，规模上界写在需求约束 C-04 里。

## 二、技术选型（5 题）

### Q5 为什么前端用 React 而不是 Vue？

**结论**：基线锁定、状态驱动表单更契合、Hook 能收敛复用。

**回答**：答题页有倒计时每秒刷新、选项即时反馈、自动保存状态三种高频状态，React 的批处理与 useEffect 清理函数对定时器和防抖的销毁更直接；在不引入 UI 组件库的前提下，倒计时和自动保存各自收敛成一个 Hook，结构更好讲。选型打分里 React 4.50、Vue 4.35，差距不大，硬约束在基线。代价是表格、弹窗、分值柱都要自研，这部分工作量体现在 15 个页面里。

**追问风险**：「Vue 更简单，为什么不用？」→ 承认学习成本更低，但基线已定，变更成本高于收益。

### Q6 后端为什么用 Express 而不是 NestJS 或 Spring Boot？

**结论**：Express 够用且成本最低，打分 4.55，NestJS 3.05、Koa 3.75。

**回答**：NestJS 的装饰器加依赖注入结构规整、可测性好，但它自带一套 DI 容器，与本项目 createApp(deps) 的手动装配是两套体系，概念冗余；引十几个包对八周工期是负收益。Koa 的洋葱模型更优雅，但社区中间件与 supertest 的配合范式不如 Express 成熟。Spring Boot 要换语言，直接违背基线。Express 的风险是结构靠约定，我用目录与单向依赖规则补上了。

**追问风险**：「Express 结构容易腐化。」→ 承认，所以加了「服务层不出现 req/res」这类可检查的约定。

### Q7 不用 ORM，手写 SQL 不怕注入和难维护吗？

**结论**：注入由参数化从机制上排除，维护靠分层与测试兜底。

**回答**：全部数据访问走 pool.query 的占位符，不做字符串拼接；集成测试用 `' OR 1=1 --`、`'; DROP TABLE users; --` 这类注入串验证，返回空结果或 400，不产生 5xx，相关表仍然存在。不用 ORM 是因为统计要 CASE WHEN 分桶、LEFT JOIN 聚合，用 ORM 要么退化成原生 SQL，要么多次往返拼装、口径分散。代价是 SQL 与索引手工维护，靠 17 个索引与 93.6% 行覆盖率兜底。

**追问风险**：「上手成本高。」→ 是，换来的是执行计划与索引可被完整讲清，这也是论文的设计论证部分。

### Q8 为什么用 JWT 而不是 Session？禁用账号怎么即时生效？

**结论**：无状态便于扩展，吊销能力靠每请求回查补上。

**回答**：前端静态托管、后端独立端口，用 Bearer 令牌只需 axios 拦截器加一行头，不用处理跨域 Cookie；令牌里带 role，前端首屏守卫可以直接用。纯无状态的代价是令牌无法吊销，所以鉴权中间件每次请求回查 users 表，校验状态与角色，管理员禁用后旧令牌立刻返回 40101。代价是每请求多一次主键查询，成本可忽略，这条登记为设计权衡 T1。

**追问风险**：「每请求查库不就失去无状态优势？」→ 单次主键查询，实测可忽略；换来禁用即时生效，是安全优先的折中。

### Q9 为什么选 MySQL 而不是 MongoDB？JSON 字段算反范式吗？

**结论**：强关系与唯一约束是正确性的一部分，JSON 只用于形状可变的字段。

**回答**：考试、试卷题目、答卷、答题明细是四级引用链，一人一卷、同卷同题不重复必须由数据库约束兜底，文档库只能靠应用层自觉；统计的五段分布用 CASE WHEN 加 GROUP BY 一次查完。JSON 只用于 options 和 answer 这两个形状随题型变化的字段，避免拆成 EAV 模型。它不是反范式，而是灵活性换约束强度：数据库不校验 JSON 形状，校验落在 QuestionService 与导入接口，由用例兜底，记在权衡 T4。

**追问风险**：「JSON 存答案怎么保证合法？」→ 三道关：题型校验、导入逐条校验、测试用例；绕过 API 直接写库仍有风险，已登记。

## 三、系统设计与难点（6 题）

### Q10 系统怎么分层？如何保证不跨层调用？

**结论**：五层加依赖单向，靠可检查的约定拦住跨层。

**回答**：调用栈恒为路由、中间件、控制器、服务、仓储：控制器只做参数校验与响应封装，服务层不出现 req 和 res，仓储层没有业务分支；服务只引用仓储接口与工具，控制器只引用服务。这样 90% 的业务规则可以在无数据库、无端口的情况下测试。代价是每层要做 DTO 映射，代码量比一路写到底多，但改一处不影响别处，论文也能逐层讲清楚为什么这么切。

**追问风险**：「约定靠自觉，怎么强制？」→ 目录审查加测试断言，代码里没有反向依赖，跨层调用在评审时能直接看出来。

### Q11 8 张表怎么支撑七步闭环？关键约束有哪些？

**结论**：以「考试—试卷题目—答卷—答题明细」为主干，把规则下沉成唯一键。

**回答**：一人一卷靠答卷表的唯一键，同卷同题不重复靠试卷题目表唯一键，指派不重复靠考生指派表唯一键，自动保存的幂等靠答题明细表唯一键配合 upsert。另外按真实查询补了 17 个二级索引，比如按考试加状态查待阅、按学生加交卷时间查历史成绩。三处有意冗余：试卷总分、答卷三项得分、本卷题分，都在事务内重算，以答题明细为唯一事实来源。

**追问风险**：「冗余分数会不会不一致？」→ 只在组卷、交卷、阅卷三个事务内写回，并提供重算语句；明细永远是事实来源。

### Q12 一人一卷和重复开考怎么保证幂等？并发会不会出两份答卷？

**结论**：先查后复用、唯一键兜底、捕获重复键回查，三段保证。

**回答**：开考先按考试加学生查，进行中直接返回原答卷；插入时由唯一键拦重复，捕获后回查返回同一份；已交卷再开考返回 409。测试里连续两次开考、20 个并发开考都只产生一份答卷。要说明的是，内存仓储没有复刻这个唯一约束，并发用例靠单线程调度顺序通过，真实兜底在 MySQL 的唯一键，这条作为残留风险 RR-05 记录在报告里。

**追问风险**：「内存模式是不是假通过？」→ 部分是，所以我把它写成风险而不是结论，并建议补上内存唯一性校验。

### Q13 超时自动交卷和手动交卷同时发生会怎样？

**结论**：两条路径只有一个成功，另一个读到既有结果，属于幂等。

**回答**：交卷在事务里先对答卷行加 FOR UPDATE，再判状态、判分、写回；写回时用「状态等于进行中」作为条件，影响行数为 0 就直接读已有结果返回。所以超时自动交卷和手动交卷撞在一起，不会重复计分，也不会把提交时间改乱。测试里连点 10 次交卷，总分与提交时间恒定。缺陷 D-01 就出在这条链路上：超时分支把提交时间写成了触发时刻，修复后改为截止时间。

**追问风险**：「没加锁会怎样？」→ 条件更新仍能拦住第二次写入，是双重保险；行锁只是让并发更早串行化。

### Q14 自动保存会不会丢答案？断线后怎么恢复？

**结论**：已保存的答案不会丢，靠单题级持久化加服务端权威恢复。

**回答**：每次选项变更先本地即时反馈，防抖几百毫秒后按单题提交，数据库用唯一键 upsert，重放没有副作用；重新打开答题页时，答卷接口返回已保存答案和剩余秒数，倒计时以服务端为准，刷新不会重置。集成用例验证了答案恢复。需要说明的是，3 秒时延与丢包重试属于网络场景，本期没有实测，测试报告标为部分通过，我没有把它写成已达标。

**追问风险**：「保存请求失败怎么办？」→ 前端标记未保存并重试，多次失败进入兜底提示；网络场景未完整实测，属残留风险。

### Q15 多选题为什么少选也不给分？判分口径怎么保证一致？

**结论**：口径一致比人性化更重要，所以少选、错选、多选一律零分。

**回答**：这条写进需求 FR-29，判分只有一处实现，多选题用集合完全相等判断，选项顺序不影响结果；用例覆盖全对、少选、多选、错选、顺序不同五种情况。如果给部分分，就要定义选对几个给几分、错选怎么扣，规则越长争议越多，成绩申诉时难以复核。代价是学生觉得苛刻，但规则可解释、可复核，这是严肃考试更需要的性质。

**追问风险**：「别的系统给部分分。」→ 那是可配置策略；本项目选择写死一种并全程一致，避免同一场考试出现两套口径。

## 四、测试与质量（4 题）

### Q16 217 条用例怎么分布？93.6% 覆盖率说明什么？

**结论**：分三层，重点打在业务规则上，而不只是「跑通」。

**回答**：119 条既有用例、63 条接口集成、35 条业务规则，合计 217 条全绿；覆盖率行 93.6%、语句 90.91%、函数 94.14%、分支 77.41%，四项都高于门禁 70/70/65/60。我更看重用例打在规则上：判分 10 条、超时交卷 7 条、开考与交卷幂等各 3 条、阅卷边界 6 条、统计口径 5 条、发布校验 1 条。覆盖率不等于正确性，8 条缺陷里 6 条是口径偏差，说明还在补。

**追问风险**：「覆盖率这么高还测不出问题？」→ 覆盖率只说明代码被执行，不说明断言够强；口径偏差正是靠新增业务规则用例才暴露的。

### Q17 测试跑在内存仓储，能证明 MySQL 下也正确吗？

**结论**：只能证明业务层正确，不能证明数据库层，这点我不回避。

**回答**：内存实现与 MySQL 实现同一套仓储接口、返回同构数据，跑的是同一份服务层代码，所以判分、状态机、统计口径的覆盖是真实的。但事务边界、唯一键冲突、SQL 参数化在内存模式下没有经过真实数据库检验，测试报告把这条列为残留风险 RR-04，建议上线前做一次 MySQL 联调。这也是我把「未接真实数据库」写进不足、而不是写进结论的原因。

**追问风险**：「那你的测试结论可信吗？」→ 业务层结论可信，数据层结论限定在代码审查范围内，两者分开表述。

### Q18 8 条缺陷都是什么？为什么还有一条没闭环？

**结论**：中 2 低 6，闭环 7 条，未闭环的 D-07 是技术债。

**回答**：最有价值的是 D-01：超时自动交卷后提交时间被写成触发时刻而不是截止时间，被业务规则用例抓出来，修复净增 11 行，回归后 217 条全绿。其余多是口径偏差，比如无简答题的答卷状态、待阅题数的类型、正确率的量纲、禁用账号的状态码，都已登记并给出处置建议。D-07 是组卷服务文件 421 行超过 400 行阈值，属技术债，不影响功能。

**追问风险**：「为什么不把 D-02 改掉？」→ 改实现会与既有断言冲突，需要先裁定口径，属于变更管理，不能为了让报表好看而改。

### Q19 有没有做性能测试？P95 达到 500ms 了吗？

**结论**：没有压测，所以不能说 P95 达标。

**回答**：测试环境没有装 k6 或 autocannon，性能这条只停留在设计目标：P95 小于 500 毫秒、P99 小于 1000 毫秒，按 200 并发 5 分钟设计。能拿出来的实测只有前端构建：gzip 主 JS 100.40 KB，低于 500 KB 门禁。设计侧给了容量估算与索引、连接池策略，但那是推演不是数据。补测方案写在残留风险 RR-01 里，答辩时我按「未测」表述。

**追问风险**：「那你凭什么说系统能用？」→ 功能与业务规则有 217 条用例支撑；性能是未验证项，不冒充已验证。

## 五、不足与展望（5 题）

### Q20 系统最大的不足是什么？

**结论**：不是功能少，而是离生产还有一段工程距离。

**回答**：具体四条：性能没有实测，只有设计目标；没有连真实 MySQL 联调，事务与唯一键只经代码审查；没有接口限流与登录失败锁定，也没有审计列与软删除；前端没有单元测试与端到端测试。另外组卷服务文件 421 行是遗留技术债。这些在测试报告里按 RR-01 到 RR-09、T6、T8 都编了号，我没有用「基本完成」这类话模糊过去。

**追问风险**：「那你觉得这个系统算完成了吗？」→ 按毕业设计门禁算完成（G1~G7 有条件通过），按生产标准还得补上面四条。

### Q21 防作弊为什么不做？如果要做怎么加？

**结论**：纯软件手段无法根治作弊，本期只做基础约束并写清边界。

**回答**：已经做的是：一人一卷，防止换号重考；截止时间由服务端计算，改本地时钟无效；指派校验保证只有被指派的学生能开考。题目乱序字段预留了，但取卷还没按答卷种子重排，这点不能算已实现。展望是切屏检测、摄像头抓拍、人脸核验、随机抽题与等值组卷，需要硬件、隐私合规与性能预算，属于后续工作。

**追问风险**：「别的系统有人脸识别。」→ 那是硬件与合规投入，超出本期范围；我选择把边界写进文档，而不是假装做了。

### Q22 AI 批改主观题可行吗？为什么现在不做？

**结论**：可行，但只能做辅助，本期明确人工阅卷。

**回答**：原因有三：没有标注语料和统一评分标准，模型给分不稳定；主观题争议大，需要可解释性与申诉链，模型很难提供；教育测量领域普遍要求人工复核。现在的数据模型已经为将来留了口子：答题明细里有得分、评语、阅卷人和阅卷时间，评分责任链是完整的。展望做法是模型预评分加教师确认，接口仍是教师提交评分，前端体验不变。

**追问风险**：「用大模型不就行了？」→ 技术上能出分，但分数要能被申诉与复核，责任链必须落在人身上。

### Q23 如果真实上线，还需要补哪些工程能力？

**结论**：补五类——数据、性能、安全、运维、前端质量。

**回答**：数据类：真实 MySQL 联调、事务与唯一键复核、备份恢复演练。性能类：k6 压测出 P95 与 P99、慢查询与索引复核。安全类：接口限流、登录失败锁定、HTTPS、日志脱敏与审计。运维类：PM2 守护与开机自启、监控告警、故障预案。质量类：前端组件测试与端到端测试，并把 421 行的组卷服务拆开。当前单机部署没有高可用，宕机即中断，这一点登记在设计权衡 T9。

**追问风险**：「这些为什么不现在做？」→ 工期与范围约束，且与毕业设计验收门禁不冲突；已按优先级写进后续动作表。

### Q24 这个系统后续可以往哪些方向扩展？

**结论**：三个方向，都不需要推翻现有架构。

**回答**：第一是题型扩展，按设计只需改答案校验与判分策略两处，接口签名和前端表单契约不变，对应可扩展性需求 NFR-16。第二是组卷策略，当前是手动选题，可以加随机抽题、按知识点与难度配比，但新增接口要走变更单，不能私自加。第三是规模化，设计里给了路径：PM2 集群、读写分离、Redis 缓存统计与试卷结构。统计侧还可以加成绩导出与题目区分度分析。

**追问风险**：「为什么现在不做随机组卷？」→ 基线只要求手动选题，加了就是超出基线的功能，不如把已有链路做扎实。
