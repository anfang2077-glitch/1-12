## 1 技术栈与工程结构

### 1.1 技术栈与依赖清单

后端以 Node.js 20+ 为运行时，Express 4 提供 HTTP 能力，MySQL 8.0 持久化数据，`mysql2/promise` 直连数据库并全部采用参数化查询，不引入任何 ORM。鉴权使用 HS256 签名的 JWT，密码使用 bcryptjs 哈希，配置读取依赖 dotenv，跨域由 cors 处理，测试使用 jest + supertest。

依赖版本严格取自 `code/server/package.json`：

| 类别 | 包 / 运行时 | 版本 | 用途 |
|---|---|---|---|
| 运行时 | Node.js | `engines.node >= 20`（本机实测 v24） | 原生 async/await、`crypto.randomUUID`、`node --watch` |
| Web 框架 | express | `^4.21.2` | 路由、中间件链、JSON 请求体解析 |
| 数据库驱动 | mysql2 | `^3.11.5` | 连接池与参数化 SQL（`mysql2/promise`） |
| 鉴权 | jsonwebtoken | `^9.0.2` | 签发与校验 JWT（HS256，8 小时） |
| 密码 | bcryptjs | `^2.4.3` | bcrypt 哈希，cost=10 |
| 跨域 | cors | `^2.8.5` | 开发期前端 5173 端口跨域访问 |
| 配置 | dotenv | `^16.4.5` | 读取 `code/server/.env` |
| 测试框架 | jest | `^29.7.0`（devDependencies） | 单元与接口测试、覆盖率统计 |
| HTTP 断言 | supertest | `^7.0.0`（devDependencies） | 直接对 `createApp` 实例发起请求，不占端口 |

工程刻意省略的三类依赖需要说明：不引入 ORM（如 Sequelize、Prisma），以保证 SQL 可控、统计聚合不被 ORM 表达力限制；不引入 zod 等运行时校验库，而是在 `src/utils/validate.js` 手写一套 zod 风格校验原语；不引入 TypeScript，以降低构建复杂度，正确性由 jest 用例保证。

### 1.2 npm 脚本

`package.json` 声明了 7 个脚本，覆盖开发、演示、初始化与测试四类场景：

| 命令 | 实际执行 | 说明 |

## 2 分层实现说明

### 2.1 调用链

一次请求的调用栈恒定如下，方向自上而下，不存在反向或跨层跳跃：

```
HTTP → app.js(requestId → cors → express.json) → routes/index.js
     → auth 中间件（JWT）→ authorize 中间件（RBAC）
     → controller（参数校验 + 响应封装）
     → service（业务规则、状态机、权限归属、判分、统计）
     → repository（mysql 实现 / memory 实现）
     → mysql2 连接池 或 内存表
```

对应的依赖规则在三层各自的 `require` 中体现：`routes/` 只引入 `controllers/`、`middlewares/` 与 `services/` 的工厂；`controllers/` 只引入 `services/` 与 `utils/`；`services/` 只引入 `repositories/` 的注入对象与 `utils/`，从不出现 `req`、`res`，因此业务层可以被 supertest 之外的单元测试直接调用。

`app.js` 是这条链路的起点，也是可测试性的关键——它只装配依赖、不监听端口：

```js
function createApp({ repos, config, clock = () => new Date() }) {
  if (!repos) throw new Error('createApp 需要注入 repos');
  if (!config) throw new Error('createApp 需要注入 config');

  const app = express();
  app.disable('x-powered-by');
  app.use(requestId);
  app.use(cors());
  app.use(express.json({ limit: config.bodyLimit || '1mb' }));
  app.use('/api', createApiRouter({ repos, config, clock }));

  // 未命中任何路由
  app.use((req, res) => {
    res.status(404).json({ code: 40401, message: '资源不存在' });
  });
  app.use(errorHandler);
  return app;
}
```

第三个参数 `clock` 是本项目测试超时逻辑的支点：生产环境取系统时间，测试时注入一个可前后拨动的时钟函数，就能在不真的等待 90 分钟的前提下验证「到点自动交卷」。

### 2.2 路由装配与注册顺序

`routes/index.js` 的流程是「先建服务、再建控制器、最后挂路由」。所有服务与控制器都由工厂函数创建，并把 `deps`（`repos`、`config`、`clock`）逐层注入：

```js
  const router = express.Router();
  const auth = createAuthenticate(deps);
  const allow = (...roles) => authorize(...roles);

  // 5.2 认证
  router.post('/auth/login', controllers.auth.login);
  router.get('/auth/me', auth, controllers.auth.me);
```

路由文件头部有关键注释：「注意路由顺序：`/exams/available` 先于 `/exams/:id`；`/grading/pending` 先于 `/grading/:attemptId`」。Express 按注册顺序匹配，若把 `/exams/:id` 写在前面，`GET /api/exams/available` 会被当成 `id="available"` 的详情请求，从而返回 40001。因此文件中先把三段学生侧具体路径（`/exams/available`、`/exams/:id/paper`、`/exams/:id/attempts`）与 `/questions/import`、`/grading/pending` 提前注册，再注册同前缀的 `:id` 路由。

按模块统计，路由共 36 条，与基线第 5 节逐条对应：认证 2 条、用户 4 条、课程 4 条、题库 5 条、考试 10 条、答题与交卷 4 条、阅卷 3 条、统计 4 条。每条路由都显式声明角色白名单，没有「只登录不限角色」的模糊地带（`/auth/me` 与 `GET /courses` 除外，二者对全部登录用户开放）。

### 2.3 控制器：只做参数校验与响应封装

控制器不含业务判断，职责被压缩到三件事：从 `req.params`/`req.body`/`req.query` 取值并校验、调用服务、用 `ok`/`created` 包装响应。异步异常统一由 `asyncHandler` 转交错误中间件，因此看不到 `try/catch` 样板：

```js
    saveAnswer: asyncHandler(async (req, res) => {
      const id = parseId(req.params.id, '答卷 ID');
      const body = requireBody(req.body);
      const questionId = requireInt(body.questionId, 'questionId', { min: 1 });
      if (!Object.prototype.hasOwnProperty.call(body, 'answer')) {
        throw badRequest('参数错误：answer 不能为空');
      }
      const data = await attemptService.saveAnswer(req.user, id, questionId, body.answer);
      return ok(res, data);
    }),
```

`parseId` 要求路径参数为 ≥1 的整数，`requireBody` 要求请求体是 JSON 对象，分页参数由 `parsePagination` 统一处理（缺省 `page=1`、`pageSize=10`，`pageSize` 上限 100，越界抛 40001）。`answer` 字段特意用 `hasOwnProperty` 判断而非真值判断，因为 `answer: null` 是合法语义（清空作答），不能被当作「未提供」。

### 2.4 服务层：注入、校验与序列化

八个服务工厂签名统一为 `createXxxService({ repos, config, clock })`，返回值是一个方法集合。服务层内部遵循三条约定：先 `requireXxx`（不存在则 40401），再 `assertXxxAccess`（越权则 40301），最后才读写仓储。响应对象一律经 `services/serializers.js` 白名单拼装，例如学生试卷题目由 `toPaperQuestion` 输出，只包含 `questionId`、`sortOrder`、`score`、`type`、`stem`、`options`，**不含 `answer` 与 `analysis`**；教师视角则用 `toExamQuestionDetail`，额外带答案、解析、难度与知识点。答案泄露面被收敛到两个函数里，便于审查。

### 2.5 三个中间件

| 中间件 | 文件 | 作用 |
|---|---|---|
| `requestId` | `middlewares/requestId.js` | 取请求头 `X-Request-Id`（长度 ≤100）或生成 UUID，写入 `req.requestId` 并回写响应头，供错误日志串联 |
| `createAuthenticate` | `middlewares/auth.js` | 校验 `Authorization: Bearer <token>`，解析 JWT 后**回查数据库**确认用户仍存在且 `status=1`，通过则挂 `req.user` |
| `authorize(...roles)` | `middlewares/auth.js` | 角色白名单，`req.user.role` 不在允许集合内时 `next(ApiError.forbidden(...))` |
| `errorHandler` | `middlewares/error.js` | 把 `ApiError` 映射为 `{code,message}` 与对应 HTTP 状态；单独识别 JSON 解析失败（`entity.parse.failed`）与请求体过大（`entity.too.large`）；未预期异常打印 `[error][requestId]` 堆栈后统一返回 500/50001，不泄露内部细节 |

鉴权中间件「每次请求回查用户状态」是一个有意的取舍：JWT 本身无状态，若只看令牌，管理员禁用某账号后旧令牌仍可用 8 小时；回查一次 `users.findById` 换来的是禁用即时生效（测试 `TC-API-06` 专门验证了这一点），代价是每请求多一次主键查询，在毕设规模下可以接受。

## 3 数据访问层双实现

### 3.1 装配与切换方式

`repositories/index.js` 是唯一的装配点，只有 6 行：

```js
function createRepositories(config) {
  if (config.driver === 'mysql') {
    return createMySqlRepositories(config.mysql);
  }
  return createMemoryRepositories();
}
```

切换由环境变量 `MYSQL_DRIVER` 决定，取值 `mysql` 时装配 MySQL 实现，**其余任何取值**都退化为内存实现：

| 场景 | 命令 / 配置 | 实际装配 | 是否写种子 |
|---|---|---|---|
| 演示、无数据库 | `npm run start:memory` | memory | 是（启动时自动 `seedMemory`） |
| 显式指定内存 | `.env` 中 `MYSQL_DRIVER=memory` 后 `npm start` | memory | 是 |
| 未配置任何 `.env` | `npm start`（`config.js` 默认 `driver='memory'`） | memory | 是 |
| 生产/联调 | `.env` 中 `MYSQL_DRIVER=mysql` 后 `npm start` | mysql，启动前 `repos.ping()` | 否（需先 `db:init` + `db:seed`） |

`index.js` 里的判断比 `config.js` 更宽一层，兼容命令行参数：

```js
  const config = loadConfig();
  const useMemory = process.argv.includes('--memory') || config.driver === 'memory';

  let repos;
  if (useMemory) {
    repos = createMemoryRepositories();
    await seedMemory(repos);
    console.log('[server] 运行模式：memory（无需 MySQL），已写入演示种子数据');
  } else {
    repos = createMySqlRepositories(config.mysql);
    await repos.ping();
```

因此 `--memory` 的优先级高于 `.env`：即使 `.env` 写着 `MYSQL_DRIVER=mysql`，`npm run start:memory` 仍会强制走内存模式，这在答辩现场没有 MySQL 服务时非常关键。

### 3.2 仓储接口

两套实现导出的方法名与参数完全一致，共 6 个仓储、57 个方法（另各有 `ping`、`close` 两个生命周期方法），服务层无需感知底层是数据库还是内存：

| 仓储 | 主要方法 | 职责 |
|---|---|---|
| `users` | `findById`、`findByUsername`、`list`、`create`、`update`、`remove`、`countAll`、`countByRole` | 用户 CRUD 与计数 |
| `courses` | `findById`、`findByCode`、`listAll`、`listByTeacherId`、`create`、`update`、`remove`、`countByTeacherId` | 课程 CRUD、代码唯一性、教师归属 |
| `questions` | `findById`、`list`、`create`、`update`、`remove`、`countAll`、`countByCourseId` | 题库分页过滤与计数 |
| `exams` | `findById`、`list`、`createWithQuestions`、`update`、`replaceQuestions`、`setStatus`、`remove`、`getQuestions`、`countQuestions`、`countAssigned`、`isAssigned`、`getAssignedStudentIds`、`assignStudents`、`isQuestionUsed`、`listForStudent`、`countAll`、`countByCourseId`、`countByCreatedBy`、`hasStudentRelation` | 考试、试卷题目、考生指派、引用检查 |
| `attempts` | `findById`、`findByExamAndStudent`、`create`、`update`、`listByStudent`、`listByExamIds`、`countByExam`、`countByStudent`、`countAll` | 答卷读写与状态过滤 |
| `answers` | `findByAttemptAndQuestion`、`listByAttempt`、`upsert`、`ensureRows`、`updateScore`、`updateGrading` | 逐题作答与得分、评语、阅卷人 |

### 3.3 MySQL 实现要点

连接池在 `src/db/mysql.js` 创建，三个参数直接决定了「时间与分数如何穿过全链路」：

```js
    charset: 'utf8mb4_general_ci',
    timezone: mysqlConfig.timezone || '+08:00',
    dateStrings: true,
    decimalNumbers: true,
    multipleStatements: false
```

`dateStrings: true` 让 `DATETIME` 直接以 `YYYY-MM-DD HH:mm:ss` 字符串返回，与内存实现、与基线的时间格式完全一致，前端可直接展示；`decimalNumbers: true` 让 `DECIMAL(6,2)` 返回 number 而不是字符串，避免前端出现 `"85.00"` 这类脏数据；`multipleStatements: false` 关闭多语句，配合全部参数化的 SQL，把注入面压到最低。

仓储内部统一使用 `db.query(sql, params)`，字段用 `AS` 起别名映射成驼峰，例如答卷仓储的字段常量：

```js
const ATTEMPT_FIELDS = `id, exam_id AS examId, student_id AS studentId, started_at AS startedAt,
  submitted_at AS submittedAt, deadline_at AS deadlineAt, status, objective_score AS objectiveScore,
  subjective_score AS subjectiveScore, total_score AS totalScore`;
```

`in (...)` 这类动态 SQL 也通过「占位符按数组长度生成、参数另外传入」的方式避免拼接：

```js
      let sql = `SELECT ${ATTEMPT_FIELDS} FROM attempts WHERE exam_id IN (${examIds
        .map(() => '?')
        .join(',')})`;
      if (statuses && statuses.length > 0) {
        sql += ` AND status IN (${statuses.map(() => '?').join(',')})`;
        params.push(...statuses);
      }
```

需要多语句原子性的场景（组卷时同时写 `exams` 与 `exam_questions`）由 `withTransaction(pool, fn)` 提供 `begin / commit / rollback` 并保证连接释放；回滚失败不会掩盖原始异常。

### 3.4 内存实现要点

内存实现以一个 `store` 模拟数据库：8 张「表」数组（`users`、`courses`、`questions`、`exams`、`examQuestions`、`examStudents`、`attempts`、`answers`）加一个自增序列，`nextId(table)` 模拟 `AUTO_INCREMENT`。各仓储文件内定义 `clone(value) => value ? { ...value } : null`，查询与写入结果都经它返回，避免调用方就地修改污染「表」数据；`createMemoryRepositories()` 每次调用都会 `createStore()`，因此每个测试文件、每个用例都能拿到互不干扰的独立数据集。

内存实现与 MySQL 实现有一处行为差异必须在论文中说明：MySQL 依靠 `uk_attempts_exam_student` 唯一索引拦截重复开考，冲突时抛 `ER_DUP_ENTRY`，服务层捕获后回读已有答卷；内存实现不产生该错误码，一人一卷完全依赖服务层「先 `findByExamAndStudent`、再 `create`」的顺序检查。由于 Node 单线程事件循环把这段逻辑切成若干微任务、且现有用例的并发开考在同一次事件循环内完成，`TC-BIZ-19` 实测仍只生成 1 份答卷；但严格意义上内存模式的并发保护弱于数据库唯一索引，这一点列入第 8 节限制。

## 4 核心业务实现

### 4.1 JWT 鉴权与 RBAC

令牌签发在 `utils/jwt.js`，payload 严格为 `{ sub, username, role }`，默认 8 小时、固定 HS256：

```js
function signToken(user, config) {
  return jwt.sign(
    { sub: user.id, username: user.username, role: user.role },
    config.jwtSecret,
    { expiresIn: config.jwtExpiresIn || '8h', algorithm: 'HS256' }
  );
}
```

校验分两步：先验签（`verifyToken`，过期与非法分别给出不同中文提示，但业务码都是 40101），再回查用户状态：

```js
function createAuthenticate({ repos, config }) {
  return asyncHandler(async (req, res, next) => {
    const header = req.headers.authorization;
    if (typeof header !== 'string' || !/^Bearer\s+\S+/i.test(header)) {
      throw ApiError.unauthorized('未登录或登录已过期');
    }
    const token = header.replace(/^Bearer\s+/i, '').trim();
    const payload = verifyToken(token, config.jwtSecret);
    const user = await repos.users.findById(Number(payload.sub));
    if (!user || Number(user.status) !== 1) {
      throw ApiError.unauthorized('账号状态异常，请重新登录');
    }
    req.user = user;
    next();
  });
}
```

RBAC 由两层构成：路由层 `authorize(...roles)` 做粗粒度角色闸门，服务层再做数据级归属判定。例如 `assertExamAccess` 要求教师的 `currentUser.id` 等于 `exam.courseId` 所属课程的 `teacherId`，`assertReadable` 要求学生的 `attempt.studentId` 等于本人 ID。这样即便某天路由白名单配置错误，服务层仍会拦住越权。需要强调的细节是：错误提示对「资源不存在」与「无权限」是有意区分的——前者返回 40401、后者返回 40301，与基线一致，便于前端给出不同文案。

### 4.2 答案标准化与判分规则

`utils/answer.js` 是判分的唯一实现处，包含题型常量、选项校验、标准答案校验、学生作答校验、判分与 `round2`。

四类题型的存储形状与判分规则：

| 题型 | `answer` 存储形状 | 自动判分 | 判分规则 |
|---|---|---|---|
| `single` 单选 | 字符串 `"A"` | 是 | 与学生作答字符串严格相等即满分，否则 0 分 |
| `multiple` 多选 | 字符串数组 `["A","C"]` | 是 | 集合完全相等才满分；少选、多选、错选均 0 分（无部分分） |
| `judge` 判断 | `"T"` 或 `"F"` | 是 | 严格相等即满分，否则 0 分 |
| `short` 简答 | 参考答案文本（≤500 字） | 否 | 不自动给分，进入待阅队列由教师打分 |

多选判分用集合比较实现，因此选项顺序不影响结果；长度不等时直接短路返回 false，避免无意义的遍历：

```js
function isAnswerCorrect(type, correctAnswer, studentAnswer) {
  if (studentAnswer === null || studentAnswer === undefined) return false;
  if (type === 'multiple') {
    if (!Array.isArray(correctAnswer) || !Array.isArray(studentAnswer)) return false;
    const correctSet = new Set(correctAnswer);
    const studentSet = new Set(studentAnswer);
    if (correctSet.size !== studentSet.size) return false;
    for (const item of correctSet) {
      if (!studentSet.has(item)) return false;
    }
    return true;
  }
  if (type === 'single' || type === 'judge') {
    return typeof studentAnswer === 'string' && studentAnswer === correctAnswer;
  }
  return false;
}
```

「标准化」体现在三层：题库入库时 `normalizeQuestionInput` 会按题型校验选项（选择题 ≥2 且 ≤6 项、key 必须为 A~F 且不重复、选项文本非空且 ≤200 字）并校验答案是否落在选项集合内；学生自动保存时 `validateStudentAnswer` 按题型校验并归一化，空多选数组归一为 `null`、空字符串归一为 `null`，从而「清空作答」与「从未作答」在库中同形；判分时再按题型选择比较策略。分值统一经 `round2` 处理（`Math.round((v + Number.EPSILON) * 100) / 100`），避免 `0.1+0.2` 类浮点尾差写进 `DECIMAL(6,2)`。

### 4.3 开考、截止时间计算与一人一卷幂等

开考入口 `examService.start` 依次校验五件事：考试存在、状态为 `published`、当前学生被指派、当前时间已过 `start_time`、当前时间未过 `end_time`；任一不满足分别抛 40401、40901、40301、40901、40901。

截止时间由「开考时刻 + 时长」与「考试结束时刻」取较早者，一行代码表达基线 4.7 的公式：

```js
      const deadlineAt = minDateTime(addMinutes(now, exam.durationMin), exam.endTime);
```

`addMinutes` 返回格式化字符串，`minDateTime` 比较时间戳后返回较早者的格式化字符串，全链路不出现 `Date` 对象穿出服务层，从根上避免时区与序列化漂移。

幂等分两段。第一段是正常路径：若已有答卷，直接复用；若已有答卷但已提交，拒绝重复开考；若已超时，先自动交卷再返回该答卷：

```js
      const existing = await repos.attempts.findByExamAndStudent(exam.id, currentUser.id);
      if (existing) {
        if (existing.status !== 'in_progress') {
          throw ApiError.conflict('您已提交该考试，不能重复开考');
        }
        const attempt = isAfter(now, existing.deadlineAt)
          ? await finalizeAttempt({ repos, attempt: existing, exam, clock, submittedAt: existing.deadlineAt })
          : existing;
        return {
          created: false,
          attemptId: attempt.id,
          deadlineAt: attempt.deadlineAt,
          remainingSeconds:
            attempt.status === 'in_progress' ? remainingSeconds(attempt.deadlineAt, now) : 0
        };
      }
```

第二段是并发兜底：两个请求同时通过「先查」后发现都没有答卷，都去 `create`，MySQL 唯一索引 `uk_attempts_exam_student` 会让后到的插入失败并抛 `ER_DUP_ENTRY`，服务层捕获该错误码后回读已有答卷，返回 `created: false`。控制器据此决定 HTTP 状态：`created === true` 返回 201，否则返回 200，因此「首次开考 201、重复开考 200」的契约行为由服务层的 `created` 标记驱动，而不是靠控制器猜。

返回体只暴露 `attemptId`、`deadlineAt`、`remainingSeconds` 三个字段。前端以 `remainingSeconds` 换算成本地时间戳做倒计时，服务端才是时间的唯一权威。

### 4.4 自动保存与越权、超时校验

自动保存是答题过程中唯一的高频写接口，`attemptService.saveAnswer` 在写库前做了四道校验，顺序经过刻意安排——先判归属，再判状态，再判超时，最后判题目归属本卷：

```js
      const now = clock();

      if (attempt.status !== 'in_progress') {
        throw ApiError.conflict('答卷已提交，不能继续作答');
      }
      if (isAfter(now, attempt.deadlineAt)) {
        await finalizeAttempt({ repos, attempt, exam, clock, submittedAt: attempt.deadlineAt });
        throw ApiError.conflict('考试已结束，答卷已自动提交');
      }

      const questions = await repos.exams.getQuestions(exam.id);
      const question = questions.find((item) => item.questionId === questionId);
      if (!question) throw ApiError.badRequest('参数错误：该题目不属于本场考试');

      const normalized = validateStudentAnswer(question.type, answer, question.options);
      await repos.answers.upsert({
        attemptId: attempt.id,
        questionId,
        answer: normalized
      });
      return { questionId, savedAt: formatDateTime(now) };
```

四个要点。其一，越权判定在方法开头完成（`attempt.studentId !== currentUser.id` 抛 40301），早于任何写操作，保证他人答卷不可写。其二，超时不是简单拒绝，而是**先自动交卷再报 40901**——这样学生刷新页面时看到的是「已交卷 + 成绩」，而不是「保存失败但答卷仍进行中」的悬空状态。其三，题目必须属于本场考试，防止用合法答卷 ID 写入无关题目。其四，写入用 `upsert`（MySQL 侧 `INSERT ... ON DUPLICATE KEY UPDATE`，内存侧按 `attemptId+questionId` 查找后覆盖），因此同一题反复保存不会产生多行，接口天然幂等，返回 `savedAt` 供前端展示「已保存 hh:mm:ss」。

超时自动交卷被设计成「读时触发」的惰性机制，`autoSubmitIfExpired` 在 `GET /attempts/:id` 与 `GET /attempts/:id/result` 中调用：

```js
async function autoSubmitIfExpired({ repos, attempt, exam, clock }) {
  if (attempt.status !== 'in_progress') return attempt;
  if (!isAfter(clock(), attempt.deadlineAt)) return attempt;
  // 超时交卷：交卷时间取 deadline_at，而非实际触发时刻
  return finalizeAttempt({ repos, attempt, exam, clock, submittedAt: attempt.deadlineAt });
}
```

不引入定时任务（服务重启即丢失），也不要求前端一定在线，代价是「最后一名学生的成绩在其下次访问时才落定」，收益是实现简单且永不漏判。

### 4.5 交卷判分状态机

答卷状态机只有三个状态、三条合法边：`in_progress → submitted`（含简答题的交卷）、`in_progress → graded`（全客观题的交卷）、`submitted → graded`（阅卷完成）。`finalizeAttempt` 是前两条边的唯一实现，也是幂等的：

```js
async function finalizeAttempt({ repos, attempt, exam, clock, submittedAt }) {
  if (attempt.status !== 'in_progress') return attempt;
  ...
  let objectiveScore = 0;
  for (const question of questions) {
    if (question.type === 'short') continue;
    const row = answerMap.get(question.questionId);
    const studentAnswer = row ? row.answer : null;
    const score = isAnswerCorrect(question.type, question.answer, studentAnswer)
      ? round2(question.score)
      : 0;
    await repos.answers.updateScore(attempt.id, question.questionId, score);
    objectiveScore += score;
  }

  const hasShort = questions.some((question) => question.type === 'short');
  return repos.attempts.update(attempt.id, {
    status: hasShort ? 'submitted' : 'graded',
    submittedAt: formatDateTime(submittedAt || clock()),
    objectiveScore: round2(objectiveScore),
    subjectiveScore: 0,
    totalScore: round2(objectiveScore)
  });
}
```

几个实现细节值得写进论文：

1. 函数首行的状态守卫是幂等的核心。重复交卷、超时自动交卷与手动交卷可能并发到达，只有第一次能从 `in_progress` 迁移出去，后续调用直接返回当前答卷，因此总分与交卷时间恒定（用例 `TC-BIZ-21` 连续交卷 10 次验证）。
2. 判分前先 `ensureRows` 为每道题补齐 `answers` 行，未作答的题也有记录（`answer` 为 NULL、`score` 为 0），这样「未作答」与「作答为空」在统计时口径一致，`countPending` 也不会漏题。
3. 逐题得分写入的是**本卷分值** `question.score`（来自 `exam_questions`），而不是题库的建议分值，符合「组卷可覆盖建议分值」的基线约定（用例 `TC-BIZ-09`）。
4. 是否有简答题决定交卷后的状态：无简答直接 `graded`，学生立即可见完整成绩；有简答则 `submitted`，先给出客观分，主观分留待阅卷。
5. 超时交卷的 `submitted_at` 取 `deadline_at` 而非检测到超时的时刻，保证成绩归属与考试窗口一致（用例 `TC-BIZ-11` 断言了这一点）。这一点与早期 README 的描述不同，以代码为准。

`submit` 方法本身只负责「必要时触发 finalize，然后回读」，返回 `{ totalScore, objectiveScore, subjectivePending }`；其中 `subjectivePending` 由 `countPending` 统计 `gradedAt` 为空的简答题数量，前端据此提示「还有 N 道简答待评阅」。

### 4.6 阅卷与总分重算

阅卷接口 `POST /grading/:attemptId` 接收 `{ items: [{ questionId, score, comment? }] }`，逐项校验后写回 `answers`，最后**全量重算**三个分数：

```js
      const answers = await repos.answers.listByAttempt(attempt.id);
      const answerMap = new Map(answers.map((row) => [row.questionId, row]));
      let objectiveScore = 0;
      let subjectiveScore = 0;
      for (const question of questions) {
        const row = answerMap.get(question.questionId);
        const score = Number((row && row.score) || 0);
        if (question.type === 'short') subjectiveScore += score;
        else objectiveScore += score;
      }
      const pendingCount = countPending(questions, answers);
      const updated = await repos.attempts.update(attempt.id, {
        status: 'graded',
        objectiveScore: round2(objectiveScore),
        subjectiveScore: round2(subjectiveScore),
        totalScore: round2(objectiveScore + subjectiveScore)
      });
```

校验规则：答卷必须已交卷（`in_progress` 抛 40901）；只能对 `short` 评分（对客观题评分抛 40001）；`0 ≤ score ≤ 该题本卷满分` 且最多两位小数；评语 ≤500 字；单次最多 50 项。写库用 `updateGrading` 同时落 `gradedBy` 与 `gradedAt`，`gradedAt` 是「是否已评」的唯一标志，`needGrading` 与 `pendingCount` 都据此推导。

重算采用「全量扫描而非增量累加」是关键设计：即便某次评分只提交 1 道题，也会把整卷的客观分、主观分、总分重新算一遍，因此不会出现历史脏数据累积导致的分数漂移；重复提交同一评分结果天然幂等（用例 `TC-BIZ-28`）。状态一律置为 `graded`，`pendingCount` 仅作为返回值告知教师「是否还有漏评」，不影响状态——这样可以多次补评，避免「必须一次评完」的强约束。

### 4.7 统计口径

统计服务把「五段分布」定义为模块级常量，避免各接口口径漂移：

```js
const DISTRIBUTION = [
  { label: '[0,60)', min: 0, upper: 60 },
  { label: '[60,70)', min: 60, upper: 70 },
  { label: '[70,80)', min: 70, upper: 80 },
  { label: '[80,90)', min: 80, upper: 90 },
  { label: '[90,100]', min: 90, upper: Infinity }
];
```

分桶前先把得分折算成百分制，并对超过满分的异常值做上限 100 的截断，再按 `upper` 逐段比较，落到第一段满足 `ratio < upper` 的桶；都不满足则落入最后一段（`upper = Infinity`），因此 100 分（含）落在 `[90,100]`：

```js
      const ratio = examTotal > 0 ? Math.min(100, (Number(attempt.totalScore) / examTotal) * 100) : 0;
      let index = buckets.length - 1;
      for (let i = 0; i < DISTRIBUTION.length; i += 1) {
        if (ratio < DISTRIBUTION[i].upper) {
          index = i;
          break;
        }
      }
      buckets[index].count += 1;
```

汇总指标集中在 `summarize`，四类口径一次算清：

```js
  function summarize(exam, attempts) {
    const count = attempts.length;
    const scores = attempts.map((attempt) => Number(attempt.totalScore));
    const sum = scores.reduce((total, score) => total + score, 0);
    const passed = attempts.filter(
      (attempt) => Number(attempt.totalScore) >= Number(exam.passScore)
    ).length;
    return {
      count,
      avg: count ? round2(sum / count) : 0,
      max: count ? round2(Math.max(...scores)) : 0,
      min: count ? round2(Math.min(...scores)) : 0,
      passRate: percent(passed, count)
    };
  }
```

三条口径必须与基线一致：

- **count**：只统计 `submitted` 与 `graded` 两种状态。所有调用点都传入 `['submitted','graded']` 作为状态过滤，`in_progress` 的答卷既不进分母也不进分布，避免「正在考试的学生拉低平均分」。
- **passRate**：`及格人数 / 参考人数 × 100`，及格判定为 `totalScore >= passScore`（等于及格线算及格，用例 `TC-BIZ-34` 专门覆盖边界），`percent` 在分母为 0 时返回 0 而不是 `NaN`。
- **accuracy**：单题正确率按「该题平均得分 ÷ 该题本卷满分 × 100%」计算，而不是「答对人数 ÷ 作答人数」。这一选择让简答题也能参与「正确率」列（按得分率呈现），代价是客观题的口径等价于「答对率」，简答题则是「得分率」，前端列名因此写作「正确率 / 得分率」并在说明区解释。

`/stats/overview` 的 7 项计数通过 `Promise.all` 并发取得；`/stats/students/:id` 先做三重权限判定（学生只能查本人、教师需与本人课程存在考生关系 `hasStudentRelation`、管理员被禁止调用该接口），再把已交卷答卷按交卷时间倒序汇总平均分。

## 5 错误码与统一响应

成功响应统一为 `{ code: 0, message: "ok", data }`；失败响应只含 `{ code, message }`，不带 `data`，避免前端误用半成品数据。`ApiError` 的四个静态工厂与 `errorHandler` 一一对应：

| 业务码 | HTTP | 语义 | 典型触发场景 | 示例 message |
|---|---|---|---|---|
| `0` | 200 / 201 | 成功 | 所有成功响应；创建成功用 201 | `ok` |
| `40001` | 400 | 参数错误 | 字段缺失、类型不符、长度越界、分页越界、时间格式错误、请求体非合法 JSON、题目不属于本卷 | `参数错误：题型取值必须为 single/multiple/judge/short` |
| `40101` | 401 | 未登录 / 令牌失效 | 缺少或格式错误的 `Authorization`、签名非法、令牌过期、账号被禁用或已删除 | `未登录或登录已过期` / `登录状态已失效，请重新登录` |
| `40301` | 403 | 无权限 | 角色不被白名单允许、教师操作他人课程、学生访问他人答卷、管理员调用仅学生可用的成绩接口 | `无权限访问该答卷` |
| `40401` | 404 | 资源不存在 | 用户 / 课程 / 题目 / 考试 / 答卷不存在，以及未命中任何路由 | `考试不存在` / `资源不存在` |
| `40901` | 409 | 状态冲突 | 已交卷后继续保存、未交卷查成绩、重复发布、仅草稿可改、课程下有题目/考试不能删、课程代码或用户名重复 | `答卷已提交，不能继续作答` |
| `50001` | 500 | 服务器内部错误 | 未预期异常（堆栈写日志，响应不含细节） | `服务器内部错误` |

三个实现约定：错误码与 HTTP 状态由 `ApiError` 构造函数一次性绑定（`new ApiError(409, 40901, msg)`），不存在「业务码说 409 而 HTTP 返 200」的可能；`errorHandler` 会识别 `entity.parse.failed` 并转成 40001，使非法 JSON 也符合契约；未预期异常只在服务端打印 `[error][requestId]`，对外一律 50001，防止泄露表名与堆栈。

分页响应的 `data` 形状为 `{ list, total, page, pageSize }`，时间统一 `YYYY-MM-DD HH:mm:ss`，布尔字段（`shuffle`、`passed`）在序列化层显式转换，避免 MySQL 的 `0/1` 直接漏到前端。

## 6 数据库初始化与种子数据

数据库为 MySQL 8.0，库名 `exam_system`，字符集 `utf8mb4`、排序规则 `utf8mb4_general_ci`、引擎 InnoDB。`src/db/schema.sql` 先 `DROP TABLE` 再重建 8 张业务表，脚本头部明确标注「仅用于开发/演示环境」，因此**绝不能在已有数据的库上执行**。

八张表与关键约束：

| 表 | 主键 / 关键约束 | 设计要点 |
|---|---|---|
| `users` | PK `id`；`uk_users_username`；`idx_users_role` | `password_hash` 长 100，容纳 bcrypt 60 字符；`status` 1/0 |
| `courses` | PK `id`；`uk_courses_code`；`idx_courses_teacher`；FK `teacher_id → users.id` | 课程代码全局唯一，教师归属为后续所有越权判定的基础 |
| `questions` | PK `id`；`idx_questions_course/type/difficulty/creator`；FK `course_id`、`creator_id` | `options` 为 JSON（简答为 NULL），`answer` 为 JSON，兼容字符串与数组 |
| `exams` | PK `id`；`idx_exams_course_status`；FK `course_id`、`created_by` | `status` 枚举 draft/published/closed；`total_score` 由组卷时累加 |
| `exam_questions` | `uk_exam_questions(exam_id, question_id)`；FK `exam_id` ON DELETE CASCADE | 同卷不重复；`score` 为本卷分值，覆盖题库建议分值 |
| `exam_students` | `uk_exam_students(exam_id, student_id)`；FK `exam_id` ON DELETE CASCADE | 覆盖式指派靠「先删后插 + 唯一约束」保证无重复 |
| `attempts` | `uk_attempts_exam_student(exam_id, student_id)`；`idx_attempts_exam_status` | 一人一卷的数据库级保证；`deadline_at` 落库而非每次计算 |
| `answers` | `uk_answers_attempt_question(attempt_id, question_id)`；FK `attempt_id` ON DELETE CASCADE | 一题一行，`upsert` 幂等；`graded_at` 作为「已评」标志 |

两张表的外键删除策略不同：试卷题目、指派、答题明细随父记录级联删除，而 `answers.graded_by` 用 `ON DELETE SET NULL`，删除阅卷教师不会连带删除答题明细。

初始化与种子是两步：

1. `npm run db:init`（`src/db/init.js`）：读取 `.env` 的 `MYSQL_*`，用一个 `multipleStatements: true` 的连接执行整个 `schema.sql`，输出「数据库及 8 张表已创建」，并提示下一步执行 `db:seed`。
2. `npm run db:seed`（`src/db/seed.js`）：先校验 `config.driver === 'mysql'`，否则打印「db:seed 需要 MySQL」并以退出码 1 结束；随后 `ping`、写入、关闭连接。写库前用 `findByUsername('admin')` 做存在性检查，已存在则报错提示「请先执行 npm run db:init 重建表」，防止重复播种。

种子数据（`src/db/seed-data.js`）覆盖基线第 8 节要求：4 个用户、2 门课程、16 道题（四种题型齐全）、2 场考试（1 场已发布并指派 2 名学生、1 场草稿）、1 份已交卷待阅答卷。考试时间窗按「运行时刻」相对生成（如开考前 1 小时至结束后若干小时），因此任何时间执行种子都能立即演示。密码统一经 `passwordHash()`（bcrypt，cost=10）写入，明文不进数据库。

## 7 运行与测试

### 7.1 命令

```bash
cd code/server
npm install
npm run start:memory      # 无 MySQL：内存仓储 + 自动种子，API 在 http://localhost:3000/api
# 或
cp .env.example .env      # 填写 MYSQL_*，并把 MYSQL_DRIVER 保持为 mysql
npm run db:init
npm run db:seed
npm start                 # 生产式启动（无热重载）
npm run dev               # 开发式启动（node --watch 热重载）
npm test                  # 全量测试（内存仓储，无需 MySQL）
npm run test:coverage     # 追加覆盖率报告
```

### 7.2 实测结果

在 `code/server` 下执行 `npm test`，实测输出为：

```
Test Suites: 10 passed, 10 total
Tests:       217 passed, 217 total
Time:        64.301 s
```

即 10 个测试文件、217 个用例全部通过，远超基线「用例 ≥40」的门禁。测试全部运行在内存仓储上，通过 `createApp({ repos, config, clock })` 直接实例化应用，不监听端口、不依赖 MySQL。需要提示的是：`README.md` 中「119 个用例」是早期记录，与当前实测不符，引用时以 217 为准。覆盖率阈值写在 `package.json` 的 `coverageThreshold` 中（行/语句 70%、函数 65%、分支 60%），`npm run test:coverage` 低于阈值会直接以非零码退出。

### 7.3 无 MySQL 时的注意事项

- 内存仓储的数据只存在于进程内，进程退出即全部丢失；每次 `npm run start:memory` 都是全新数据集，因此演示前不必「清理脏数据」，但也不能用它做持久化演示。
- 内存模式固定单进程；无法通过多开进程模拟多实例部署，也无法验证数据库唯一索引在并发下的行为。
- 内存实现不产生 MySQL 错误码（如 `ER_DUP_ENTRY`），相关兜底分支在内存模式下不会被触发，覆盖率统计也不包含 `repositories/mysql/**`。
- 若 `.env` 已按样例填写 `MYSQL_DRIVER=mysql` 但本机无 MySQL 服务，`npm start` 会在 `repos.ping()` 阶段抛 `ECONNREFUSED`，入口会打印提示「无 MySQL 环境时请使用 npm run start:memory」。
- 端口冲突时（默认 3000）需改 `.env` 的 `PORT`；前端 `vite.config.js` 的代理目标同步调整。

## 8 已知限制与改进方向

1. **无防作弊机制**。系统只有「一人一卷 + 服务端时限 + 服务端判分」三项基础约束，没有切屏检测、摄像头监考、人脸识别、IP/设备指纹。改进方向：前端监听 `visibilitychange` 记录切屏次数并上报，服务端把这些事件落成 `attempt_events` 表，作为事后复核依据。
2. **统计为实时聚合，未做缓存**。`/stats/exams/:id` 每次请求都重新拉取该场次全部答卷并逐份遍历答题明细，复杂度约为 O(答卷数 × 题数)，答卷上千后会明显变慢。改进方向：把场次统计结果物化到 `exam_stats` 表，在交卷/阅卷完成时增量更新，或引入 Redis 缓存并按时段失效。
3. **单进程内存仓储不持久**。内存实现仅用于演示与测试，进程重启即丢数据，且无法在多进程/多实例间共享。改进方向：内存实现只保留在测试装配中，演示环境改为 SQLite 或容器化 MySQL；若坚持内存演示，可加一层「启动时从 JSON 快照恢复」。
4. **超时自动交卷依赖「读时触发」**。若学生开考后关闭页面且不再访问，答卷会一直停留在 `in_progress`，直到有人（学生本人或教师）访问相关接口才落定。改进方向：增加一个轻量调度器（如每分钟扫描 `deadline_at < now AND status='in_progress'`），或由数据库事件/队列补偿。
5. **乱序发卷未实现**。`exams.shuffle` 字段已持久化、接口已按契约返回，但发卷逻辑没有按答卷固定种子打乱题序，属于「字段预留、功能未落地」。改进方向：以 `attemptId` 为种子做 Fisher-Yates 洗牌，在 `paper` 与 `attempt.get` 中统一应用，保证同一答卷多次进入题序稳定。
6. **提交阅卷非全事务**。`grade` 逐项 `updateGrading` 后再更新 `attempts`，若中途异常，可能出现「部分题已评分、总分未重算」的中间态（用例 `TC-BIZ-24` 通过前置校验避免了越界写入，但网络中断仍可能留下半成品）。改进方向：把整段阅卷写入包进 `withTransaction`（`db/mysql.js` 已提供该能力，目前只有考试仓储的组卷、替换题目、删除与指派四处使用，阅卷路径尚未使用）。
7. **无审计日志表**。目前只有 `requestId` + `console.error` 的控制台日志，缺少「谁在何时改了哪条数据」的持久审计。改进方向：增加 `audit_logs` 表，在 service 层对写操作记录操作者、目标、前后值摘要。
8. **限流与幂等键缺失**。登录接口没有失败次数限制或验证码，理论上可被暴力尝试；自动保存是高频写，缺少客户端幂等键与限流保护。改进方向：接入 `express-rate-limit`，登录按 IP + 用户名双维度限流，并对 `PUT /attempts/:id/answers` 加每答卷 QPS 上限。
9. **内存仓储的并发保护弱于数据库**。一人一卷在 MySQL 下由唯一索引兜底，在内存模式下仅靠服务层「先查后建」，并发窗口理论上存在。改进方向：在内存 `attempts.create` 中同样做唯一性检查并抛出与 `ER_DUP_ENTRY` 同形的错误，使两套实现行为完全对齐。
10. **文档与代码存在个别漂移**。例如 `README.md` 的用例数（119）与实测（217）不一致，早期对超时交卷 `submitted_at` 的描述也与当前实现（取 `deadline_at`）不同。改进方向：把关键数字（用例数、覆盖率、错误码）纳入测试断言或构建脚本自动生成，避免手写文档过期。
