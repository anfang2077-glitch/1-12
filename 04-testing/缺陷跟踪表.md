## 2 缺陷明细

### D-01 超时自动交卷的 `submitted_at` 记为触发时刻而非 `deadline_at`

| 项 | 内容 |
|---|---|
| 严重级 | 中 |
| 类型 | 代码缺陷 |
| 模块 | 在线答题 / 交卷（`src/services/attempt.js`、`src/services/exam.js`） |
| 关联需求 / 用例 | FR-30（验收标准 3）、NFR-11；TC-30-1、TC-BIZ-11、TC-BIZ-12、TC-BIZ-17 |
| 发现阶段 | P3 业务规则测试（红灯：3 条超时用例失败；另 1 条为用例自身前置设置问题，已修正） |
| 状态 | 已关闭（已修复，回归通过；**QA 代修，待 BE 复核**） |

**复现步骤**

1. 教师组卷（60 分钟）→ 发布 → 指派 student01。
2. 学生开考，保存第 1 题答案。
3. 将注入时钟推进 `60 分钟 + 5 秒`（模拟超时）。
4. `GET /api/attempts/:id` 触发自动交卷。
5. 读取 `attempts.submitted_at`。

**实际结果**：`submitted_at = 2026-10-31 18:20:25`（触发时刻），`deadline_at = 2026-10-31 18:20:20`。
**预期结果**：`submitted_at` 等于 `deadline_at`（SRS FR-30 验收标准 3「误差 ≤ 1 秒」、UC-31 主流程 3「记为 deadline_at，确保成绩归属与考试窗口一致」）。

**根因**：`finalizeAttempt()` 统一用 `formatDateTime(clock())` 写入 `submitted_at`，无法区分「手动交卷」与「超时交卷」；4 个调用点（`autoSubmitIfExpired`、`saveAnswer` 的超时分支、`submit` 的超时分支、`exam.start` 复用超时答卷分支）均未传入截止时间，导致超时答卷的提交时间落在考试窗口之外。

**修复（≤15 行，QA 代修，待 BE 复核）**

```js
// src/services/attempt.js
async function finalizeAttempt({ repos, attempt, exam, clock, submittedAt }) {
  ...
  submittedAt: formatDateTime(submittedAt || clock()),   // 超时交卷传入 deadline_at
}

async function autoSubmitIfExpired({ repos, attempt, exam, clock }) {
  if (!isAfter(clock(), attempt.deadlineAt)) return attempt;
  return finalizeAttempt({ repos, attempt, exam, clock, submittedAt: attempt.deadlineAt });
}
```

```js
// src/services/attempt.js —— saveAnswer 超时分支
await finalizeAttempt({ repos, attempt, exam, clock, submittedAt: attempt.deadlineAt });

// src/services/attempt.js —— submit 分支
const now = clock();
const expired = isAfter(now, attempt.deadlineAt);
attempt = await finalizeAttempt({ repos, attempt, exam, clock, submittedAt: expired ? attempt.deadlineAt : now });

// src/services/exam.js —— 开考时复用已超时答卷
? await finalizeAttempt({ repos, attempt: existing, exam, clock, submittedAt: existing.deadlineAt })
```

改动量：净增 11 行（其中 4 行为中文注释），未改变任何外部接口、错误码与响应字段。

**回归结论**：修复前 TC-BIZ-11/12/17 失败（`Expected "18:20:20" Received "18:20:25"`）；修复后三条用例全部通过，且**未超时的手动交卷仍写当前时间**（TC-BIZ-21 断言 `submitted_at` 恒定）。全量 `npm test` 217/217 通过，行覆盖率 93.6%。**待 BE 复核点**：`submitted_at` 是否应统一按「服务端受理时刻」记账（若产品口径变更，需同步修订 FR-30 并回滚本修复）。

### D-02 无简答题试卷交卷后状态直接为 `graded`

| 项 | 内容 |
|---|---|
| 严重级 | 中 |
| 类型 | 代码缺陷（状态语义） |
| 模块 | 交卷 / 状态机（`src/services/attempt.js` `finalizeAttempt`） |
| 关联需求 / 用例 | FR-29（验收标准 9）、SRS §7.2 A-08、基线 §4.7；TC-29、TC-29-3 |
| 发现阶段 | P3 接口集成测试（代码走查 + 用例观察） |
| 状态 | 已关闭（已评估，按现状保留；**已知问题**，待 BE/SA 裁定） |

**复现步骤**：组卷仅含 2 道单选题（无简答）→ 发布、指派 → 学生开考并交卷 → `GET /api/attempts/:id`。

**实际结果**：`status = "graded"`。
**预期结果**：`status = "submitted"`（FR-29「提交后 attempts.status="submitted"」；A-08「交卷后若无简答题需人工评分，状态仍为 submitted，不自动跳 graded」）；基线 §4.7 中 `graded` 的语义是「已人工阅卷完成」。

**根因**：`finalizeAttempt()` 中 `status: hasShort ? 'submitted' : 'graded'`，把「自动判分完成」等同于「已阅卷」。

**影响**：`status` 语义失真（未人工阅卷却显示已批阅）；学生成绩页与统计页把自动判分答卷显示为「已批阅」。分数本身不受影响，统计口径同时包含 `submitted` 与 `graded`，`/grading/pending` 因 `pendingCount=0` 也不会误列。

**处置**：**QA 不代修**。原因：既有后端用例 `tests/attempts.test.js`「B28 不含简答题的试卷交卷后直接 graded」已将该行为锁定为断言，修改实现会使既有用例失败，属于「测试断言与需求冲突」，须由 BE 与 SA 先裁定「无简答题时是否允许自动进入 graded」。裁定后二选一：① 改实现并在既有用例中同步修正断言（推荐，符合 FR-29/A-08）；② 修订 FR-29 与 A-08，明确「自动判分完成即 graded」。

**回归结论**：本轮新增用例只断言分数与待阅数量（TC-BIZ-01/07/08），不对该状态做反向断言，避免与既有断言冲突；该差异作为已知问题登记。

### D-08 答题页恢复时读取 `lastSavedAt`，后端 `GET /attempts/:id` 未返回该字段

|---|---|
